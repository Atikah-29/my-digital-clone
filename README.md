# Atikah's Digital Clone (Hybrid RAG)

> **This is an AI clone, not the real person.**

A chatbot that answers questions as me, using only documents I wrote about myself. It uses Retrieval-Augmented Generation (RAG) with BM25 keyword search, dense embedding search, and Reciprocal Rank Fusion (RRF). The UI is built with Streamlit and the answers are generated by an LLM through the Groq API.

**Live demo:** https://my-clone-mhk8unzxnw5qpbhracuurd.streamlit.app/
**Code repository:** https://github.com/Atikah-29/my-digital-clone

*Deployment note: as permitted by the instructor (Sir Saad Mansoor), this project uses Streamlit Community Cloud and GitHub instead of Hugging Face Spaces.*

---

## How it works

1. **Load and chunk:** documents in `data/` are split into overlapping chunks of about 200-300 words. Each chunk keeps its source file name and chunk ID.
2. **Index twice:** a BM25 index (`rank_bm25`) is built over tokenized chunks, and a sentence embedding (`sentence-transformers`, `all-MiniLM-L6-v2`) is computed for every chunk. Embeddings are precomputed once and saved to `embeddings.npy`; chunk text and metadata are saved to `chunks.json`.
3. **Retrieve:** the user picks a mode: **BM25 only**, **Dense only** (cosine similarity with numpy, no vector database) or **Hybrid**.
4. **Fuse:** Hybrid mode merges both rankings with Reciprocal Rank Fusion: `score = sum(1 / (60 + rank))`.
5. **Generate:** the top chunks and the question are sent to the LLM with a persona prompt. It must answer in first person, only from the context, and say "I don't have that in my notes." when the answer is not there.
6. **Show the work:** the app displays the answer plus the retrieved chunks with their source file, chunk ID and score.

## How to run locally

```bash
pip install -r requirements-local.txt
python build_index.py          # chunks data/ and saves chunks.json + embeddings.npy
```

Set your API key as an environment variable (never put it in the code):

```powershell
# Windows PowerShell
$env:GROQ_API_KEY="your_key_here"
```

```bash
# macOS / Linux
export GROQ_API_KEY="your_key_here"
```

Then start the app:

```bash
python -m streamlit run streamlit_app.py
```

## API key handling

The Groq API key is **not** stored in the code or the repository. Locally it is read from the `GROQ_API_KEY` environment variable. On Streamlit Community Cloud it is stored in the app's **Secrets** settings (the equivalent of a Space secret).

## 1. Knowledge base and why I chose it

I used **12 documents (~15 pages)** written by me, all in Markdown, covering the required mix:

| File | Type | Content |
|---|---|---|
| `bio.md` | Factual | Who I am, background |
| `cv.md` | Factual | Education, skills, experience |
| `courses.md` | Factual | Courses I have taken |
| `faq.md` | First-person FAQ | 25+ questions answered the way I would answer |
| `favorites.md` | Personality / opinion | Favorite things |
| `opinions.md` | Personality / opinion | Values and hot takes |
| `goals.md` | Personality / opinion | Career and personal goals |
| `study_habits.md` | Long-form | How I study and work |
| `projects.md` | Long-form | Overview of my projects |
| `project_rag_career.md` | Long-form | RAG career project write-up |
| `project_sentinelguard.md` | Long-form | SentinelGuard project write-up |
| `project_smart_environment.md` | Long-form | Smart environment project write-up |

**Why these documents:** I chose documents about my studies, projects, and personal interests because I can immediately judge whether the clone's answers are correct. The FAQ file gives the clone my real voice, the project write-ups contain rare keywords (like "SentinelGuard") where BM25 should do well, and the descriptive opinion/personality text lets dense search handle paraphrased questions.

**Privacy check:** no phone numbers, addresses, CNIC or other ID numbers, passwords, account details, private chat logs, or private information about other people are included.

**Chunking:** about 200-300 words per chunk with a 40-word overlap. Each chunk stores its source file and chunk ID, giving **24 chunks** in total.

## 2. Retrieval comparison: 5 test questions

Top result per mode (format: `file#chunk_id (score)`). Q1 is built around an exact rare keyword, and Q2 is a paraphrased question that shares no words with the answer.

| # | Question | BM25 result | Dense result | Hybrid (RRF) result | Best mode and why |
|---|---|---|---|---|---|
| Q1 (rare keyword) | What is SentinelGuard? | project_sentinelguard.md#0 (12.4) | project_sentinelguard.md#0 (0.65) | project_sentinelguard.md#0 (0.032) | **BM25** - the exact term "SentinelGuard" appears in only one chunk, so the keyword match ranks it first. |
| Q2 (paraphrase) | What are you building for your final year? | projects.md#1 (4.2) | project_sentinelguard.md#1 (0.58) | project_sentinelguard.md#1 (0.028) | **Dense** - BM25 found no exact words from the query, but embeddings matched the meaning of "building for final year" to the SentinelGuard project. |
| Q3 | What advice would you give a junior student? | study_habits.md#0 (8.1) | study_habits.md#2 (0.61) | study_habits.md#0 (0.030) | **Dense** - matched the semantic concept of advice/guidance better than the exact word "junior". |
| Q4 | What are some of your favorite things? | favorites.md#0 (9.5) | favorites.md#0 (0.72) | favorites.md#0 (0.033) | **Hybrid** - both exact word match and semantic context aligned on the favorites file. |
| Q5 | Who is your favorite superhero? | favorites.md#1 (1.2) | opinions.md#0 (0.21) | favorites.md#1 (0.015) | **None** - this is not in the documents, and the clone correctly said "I don't have that in my notes." |

**Summary:** BM25 won on exact names and tools, dense search won on paraphrased and opinion questions, and Hybrid was the most reliable overall because it recovers whichever retriever missed.

**Fusion method:** I implemented **Reciprocal Rank Fusion** (`score = sum(1 / (60 + rank))`), which works from ranks and so needs no score normalization. The alternative is **weighted score fusion** (`alpha * dense + (1 - alpha) * bm25` after min-max normalizing each score), which allows tuning how much each retriever counts but is sensitive to score distributions. I chose RRF because BM25 and cosine scores are on very different scales.

## 3. Failure case

**Question:** Who is your favorite superhero?
**What the clone answered:** "I don't have that in my notes."
**Why it matters:** The fact is missing from my documents, but retrieval still returned chunks about my favorites (such as `favorites.md#1`) because the word "favorite" matched. Both retrievers rank by similarity, not by whether the chunk actually answers the question, so they always return something. Only the grounded prompt stopped the LLM from inventing an answer. This shows that retrieval alone cannot tell "relevant topic" from "contains the answer", which is a weakness the improvement below addresses.

## 4. One improvement for next time

Next time, I would implement a cross-encoder reranker over the hybrid results. Currently, RRF combines BM25 and Dense, but a cross-encoder would read the top 10 chunks together with the question and re-order them, which fixes cases where a chunk has a high keyword score but lacks the actual answer.
